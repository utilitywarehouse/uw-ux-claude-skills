The `ux` plugin currently ships twelve skills. Every command below runs under the `ux:` prefix — see [Plugins and Skills](/concepts/plugins-and-skills/) if that's new to you, or [Install](/install/) to get set up. All twelve get a full deep-dive page now — start with whichever paragraph matches what you're trying to do. Unfamiliar term in one of the descriptions below? Check the [Glossary](/knowledge-base/glossary/).

## Using it day to day

Once you're set up, these are the skills you'll come back to again and again.

- **Starting a new session.** At the start of a session, tell Claude what you're working on, or ask it to run `/ux:new-session`. It lists your active projects and loads the right one, so you don't have to spell out a folder path. See the [full walkthrough](/skills/new-session/).

- **Starting your next project.** Your first project already got set up for you automatically during the initial setup of the knowledge base. From now on, you don't need to run anything. Just tell Claude you're starting something new, and it sets up the right folders for you using `/ux:new-project-setup`. See the [full walkthrough](/skills/new-project-setup/).

- **Sharing knowledge with the team.** Claude keeps watch over your whole knowledge base. If you edit or add to something already shared, it picks that up on its own, opens a pull request, and a knowledge base admin reviews it before it goes out to the team. If Claude spots something completely new that looks worth sharing, it gives you the option to turn it into shared knowledge and contribute it back. See the [full walkthrough](/skills/contribute-to-shared-knowledgebase/) for what that looks like.

- **Keep your knowledge base healthy over time.** Run `/ux:knowledgebase-health-check` periodically. Good times to run it: after adding a lot of new content at once, or just when it's been a while. It catches broken links, contradictions in your knowledge, and stale rules. See the [full walkthrough](/skills/knowledgebase-health-check/) for details.

- **End each working session with `/ux:end-session`.** A "session" is just one sitting of working with Claude Code — however long you're at it before you close the window or walk away. Ending a session properly, with this skill, captures durable knowledge, changed project facts, and new rules before any of it gets lost. See its [full page](/skills/end-session/).

## setup-my-knowledge-base

Sets up a brand-new personal knowledge base from scratch: the core PARA folders, a starter `CLAUDE.md`, an interview-driven `About Me` note, a `Start here` note, and links into all of the team's shared content (the Research Repository and every shared product wiki) — then hands off to `new-project-setup` so you leave with one real project, not a demo. Only ever runs once per knowledge base. **[Full page →](/skills/setup-my-knowledge-base/)**

## new-project-setup

Sets up a new project folder inside `1-Projects/`, branching on whether it's a brand-new top-level product area (with a Wiki shared with the team by default) or a sub-project within an existing area. Confirms the project is actually new, asks a handful of focused questions, and leaves the workspace ready to go immediately. **[Full page →](/skills/new-project-setup/)**

## new-session

Works out which knowledge-base project a session is about, right at the start, by scanning `1-Projects/` directly and offering back a short grouped list — instead of leaving Claude blind to it until you open the exact folder or spell out a path. Skips the list if your opening message already answers the question, flags projects missing a `CLAUDE.md` instead of silently dropping them, and falls back to `4-Archives/` or `new-project-setup` when nothing active matches. A `SessionStart` hook nudges Claude to offer it automatically. **[Full page →](/skills/new-session/)**

## research-transcript-cleaner

Cleans raw video transcripts from UX research sessions with participants — moderated interviews, usability tests, unmoderated recordings — into a coding-ready markdown file, using **intelligent verbatim**: hesitation and meaning are preserved, filler and inconsistency are removed, without rewriting what participants actually said. Triggers on a pasted or uploaded `.vtt`/`.srt`/`.txt`/`.docx` transcript, or a Dovetail/Userlytics/Meet/Zoom/Teams export. Not for internal meetings or standups — those have no research participant to code. **[Full page →](/skills/research-transcript-cleaner/)**

## research-transcript-coder

Takes a cleaned transcript and applies qualitative codes ready for thematic analysis, maintaining a shared codebook across every session in a study so cross-session synthesis stays consistent. Pairs naturally after `research-transcript-cleaner` finishes. Like the cleaner, it's for sessions with an actual research participant — not internal meetings. **[Full page →](/skills/research-transcript-coder/)**

## study-writeup

Writes up a finished piece of research as a full report (may name participants, UW-internal, filed with the owning project and mirrored into the Research Repository) and a one-page study card (never names participants, shareable anywhere the knowledge base is shared). Detects what already exists — nothing, report-only, card-only, or both — and does only the work that state needs. Every figure is verified against a source before it's written, and when starting from raw or coded data the skill also does the thematic-clustering analysis itself. **[Full page →](/skills/study-writeup/)**

## knowledgebase-health-check

Audits the health of the whole knowledge base — not just one wiki — for orphaned notes, broken links, stale Routing Map rows, a root `CLAUDE.md` that's drifted from the shared starter template, missing symlinks into shared content, plain-filename citations that read as unconnected, stale pages, and page-format violations. Runs the mechanical link-check and the substantive content review together, rather than treating either as optional. Worth running after a bulk ingest, a folder reorganisation, or whenever graph view looks sparser than it should. **[Full page →](/skills/knowledgebase-health-check/)**

## end-session

An end-of-session capture pass that reviews what just happened for anything that should outlive the session, then routes each finding to the right home — durable product knowledge to the area Wiki, changed project facts to `MEMORY.md`, new behaviour rules to `CLAUDE.md`, cross-session facts to auto-memory, personal facts to `About Me.md`, standing design heuristics to `Design Principles.md` — proposing every change for approval before writing anything. Triggered by saying the session's wrapping up, or when something substantial landed mid-session and hasn't been written down yet. **[Full page →](/skills/end-session/)**

## contribute-to-skills-repo

Ships any finished change to this repo — a new skill, an edit, a retirement, or a docs-only wording fix — into a pull request for repo admins to review and merge. Runs this repo's smoke test for the skill before every push. Never merges anything itself: `main` is protected, and only a repo admin approves the merge. This is literally how this documentation site's own source skills got written up — see [Contribute](/contribute/). **[Full page →](/skills/contribute-to-skills-repo/)**

## contribute-to-shared-knowledgebase

Takes an edit already made inside a symlinked shared folder (the Research Repository, or a product wiki) and turns it into a pull request against `uw-knowledgebase-content` — handling the pull, branch, commit, push, and PR so the contributor never has to type a raw `git` command. Doesn't apply to edits inside your own private folders (`0-Inbox`, personal project work) — only shared content goes through a PR. **[Full page →](/skills/contribute-to-shared-knowledgebase/)**

## figma-craft

Execution-level craft for hands-on Figma design work — a set of hard-won gotchas around effect styles, frame fills, Hearth component quirks, and semantic colour choices. A companion layer that sits underneath whichever Figma tool is actually driving the calls, holding the properties of Figma and Hearth that are true in any file, rather than one file's own local conventions. **[Full page →](/skills/figma-craft/)**

## figma-dev-handoff

Turns a working Figma journey page into a dev-ready one: converts loose screens into component sets, files them on the file's master-components page, places instances back on the journey page, and keeps every engineering annotation visible where developers actually read it. Deliberately not a manual process — the sequence has five silent failure modes that destroy annotations or ship mangled text to engineers if done by hand. **[Full page →](/skills/figma-dev-handoff/)**
